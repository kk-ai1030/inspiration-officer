## 0. 一句话

这一轮把系统从「只记录偏好」推进到「有真实结果标签 → 可被外部 agent 离线调用 → 能如实观测自己还没闭合 → 有独立但需人工确认的校准通道」。做得最扎实的是**隔离**与**诚实**；最薄弱的是**出口一致性**（MCP 绕过了 B4 的脱敏设计）和**最后一公里接线**（确认后摘要不自动刷新）。

## 2. 设计上守住的几条线

1. **一主两投影不变**：本机 `--state-dir` 是唯一权威；云端沙箱里的状态、平台记忆都只是投影。B4 的摘要是「只读聚合」，不是第二份权威数据。
2. **提议 + 确认，不悄悄改行为**：权重提议要 `--confirm`；校准提议也要 `--confirm`；`apply()` 会拒绝权重类校准提议；网页与 MCP 都不能代用户确认。
3. **两套标签严格分开**：`verdicts.jsonl` 的采纳率驱动 `p̂` / `Δw`；`outcomes.jsonl` 的结论成立率只走独立校准通道。回归测试 C-2 锁死「删掉 `outcomes.jsonl` 前后，`feature_stats` 与权重提议完全一致」。
4. **默认零风险**：B2 的额外来源默认关闭；使用画像默认关闭；B7 的脚本恒不执行；MCP 支持 `--read-only`。
5. **失败落在安全一侧**：摘要缺失时明确回答「周报需要在本机运行」，而不是编数字；空状态的飞轮明确说「尚未开始转动」；样本不足只记录不提议。
6. **不假装已闭环**：观测台列出的 `not_consumed` 是真实缺口，不把「有提议」写成「已生效」。

## 4. 当前实现的已知问题清单

> 状态均为「未修」，按优先级分组。编号便于认领；改完请补回归测试。

### P0 · 目标与隐私

| 编号 | 问题 | 影响 |
|---|---|---|
| N01 | **飞轮仍未闭合**：唯一自动回流是「评价 → p̂ → 权重提议 → 人工确认 → 排序」；`outcomes.jsonl`、`implicit.jsonl`、`profile/interests.md` 三条仍不消费。③ 只是把真实结果从「只展示」升级成「写卡提示」，仍需人工确认、不进排序 | 「越用越好用」目前仍靠人，不是自动机制 |
| N02 | **没有效果验证回路**：校准提示生效后，未按 `calibration_id` 比较应用前后的 `confirmed_rate`，无 A/B、无停用对照 | 无法回答「这条提示有没有让建议更准」 |
| N03 | **B4 脱敏边界与 MCP 冲突**：`insp_list_verdicts` 返回含 `reason` 的原始评价行、`insp_get_card` 返回标题与逐字引文、`insp_weekly_report` 返回完整本地周报（含实测摘录、回访 `card_id`）。`scrub()` 只按正则去掉绝对路径，不做字段白名单 | 同一份数据存在「脱敏」与「不脱敏」两个出口；客户端可以是云端 agent |
| N04 | **`insp_calibration` 返回完整 `build()`**，含自由文本 `by_subfield`；而 `verdict_summary.py` 特意剔除了该字段 | MCP 绕过了摘要的白名单标准 |
| N05 | **`--read-only` 覆盖不全**：`WRITE_TOOLS` 只有三个写工具，但 `insp_verdict_summary` 在 `write=true` 时也会落盘，且仍出现在 read-only 的 `tools/list` 中 | 「隐藏并拒绝写工具」的承诺不完整 |

### P1 · ③ 的接线与一致性

| 编号 | 问题 | 影响 |
|---|---|---|
| N06 | **`--confirm` 后不刷新 `verdict_summary.json`**：`apply()` 只写 `taste/calibration.json`，不调用 `verdict_summary.write()`；摘要只在 `receiver.sync_back()` 入库成功时重生成 | 确认后若不再跑一轮，生效提示永远到不了 `insp-card`；测试 C-7 是直接调 `VS.build()` 验证的，未覆盖文件级链路 |
| N07 | `taste/calibration.json` 未登记进 `receiver.STATE_FILES` / `publish_state.STATE_FILES` | 生效提示没有独立通道，完全依赖摘要刷新时机 |
| N08 | `calibration_id = "cal-<日期>"`：同日重新 `--write` 覆盖提议文件；已应用过的 id 让当天后续确认被「已应用过」拒绝 | 一天内只能应用一次，需改天或手改 |
| N09 | `--config` 是空保留位，`MIN_N=3` / `MIN_GAP=0.2` 硬编码 | 与「学习参数全在 `config.json → weights.learning`」的约定相悖 |

| N11 | **口径混淆**：第 10 节「采纳率」= 该类型全部显式评价里采纳类占比，第 1 节 = 本周采纳 / 本周推送 | 同名不同义，用户易误读 |
| N12 | `unknown` / `abandoned` 回填被丢弃；`retract` 不删回填但采纳率按评价栈算 | 丢失「采纳了却没做」这一强信号；可能出现「有结果却无评价」的卡计入 `n` 却不计入对照分母 |
| N13 | `scrub()` 的路径正则只覆盖盘符 / `/Users/` / `/home/`，不覆盖 UNC 路径、邮箱、UUID | 隐私过滤不完整 |

## 5. 建议的处理顺序

1. **N03 / N04 / N05 / N13**：统一 MCP 出口的字段白名单，或在契约中明确「MCP 属于可信通道」并提供脱敏模式；把 `insp_verdict_summary` 纳入写工具管理。
2. **N06 / N07**：`apply()` 成功后刷新 `verdict_summary.json`；把 `taste/calibration.json` 登记进推送清单；补一条文件级链路回归。
3. **N09 / N10 / N11 / N12**：门槛移入 `config.json`；抽取公共聚合函数收敛重复实现；统一采纳率命名口径；把 `abandoned` 纳入观测。
4. **N01 / N02**：加「提示生效后的效果验证」（按 `calibration_id` 分组比较 `confirmed_rate`），再讨论是否允许真实结果影响配额 / 排序——这是让飞轮真正闭合的一步，需要单独的数据契约与 `--confirm` 保障。
5. **N14–N19**：升版、补 CHANGELOG 与 backlog 编号、收紧 `g1` 判定、状态目录加锁或单会话检查、MANIFEST 自动校验、清理残留。
