# 运行协议（v1.5.0）

v1.4 起灵感机制**只在用户手动触发时运行**，取消所有定时任务（平台定时任务和 Windows 计划任务都不用）。原因见测评报告：平台定时任务读不到工作区文件；而“用户主动说一句”这个动作本身就保证有人在场。

## 1. 三种触发方式，一套产物

| 触发方式 | 谁发起 | 状态怎么进沙箱 | 结果怎么回本地 |
|---|---|---|---|
| ① 网页里 @灵感官：“主动探索灵感” | 用户 | 记忆里的 `[灵感配置]` / `[灵感状态]` + 会话沙箱里上次留下的状态；都没有就从模板自举 | 本地收货员轮询最近会话，读 `bundle.json` |
| ② 评价页按钮“主动探索灵感” | 用户点击 → `receiver.trigger_run` | 收货员把本地 `state.json` 等文件作为附件上传（`/workspace/_refs/`） | 收货员盯着这次运行，跑完立刻收货 |
| ③ 本地兜底 `run_local.py` | 用户手动执行，或收货员在 `FETCH_BLOCKED` 时自动拉起 | 本地抓取、预筛（全文模式再抓原文），再连同状态一起上传 | `run_local.py` 自己收货 |

三种方式最后都产出同一个整包（`insp-bundle/1.0`），收货规则也一样。

## 1b. 论文读取模式（v1.4.1，一个配置字段切换）

本地 `config.json` 的 `"arxiv_fetch_mode"` 决定每次运行怎么读论文：

| 取值 | 做什么 | 卡片证据 | 卡片链接 | 用时 |
|---|---|---|---|---|
| `"abstract"`（**默认**；不写、写错也是它） | 只用 arXiv 列表里的标题 + 摘要 | `source.quote` 摘要逐字片段 | `source.url` = arXiv 摘要页 | 基准 |
| `"fulltext"` | 另外逐篇抓候选论文全文 + 相关文献全文 | 另需 `fulltext_quotes`（正文引文）+ `related_evidence` | `source.url` + `source.fulltext_url`（读过的 HTML/PDF） | 约 4–5 倍 |

模式怎么到达每条路径：

| 触发方式 | 模式来源 |
|---|---|
| ② 评价页按钮 | 收货员每次触发时重新读 config.json，把 `--fetch-mode X` 写进指令 |
| ③ 本地 `run_local.py` | 直接读 config.json；摘要模式不抓、不上传原文 |
| ① 网页里 @灵感官 | 记忆 `[灵感设置]`（收货员在 config 变化后自动同步，或手动 `receiver.py --sync-settings`）；用户本次明确说“通读全文 / 只看摘要”时以用户为准；都没有 → `abstract` |

整包和 `triage.json` 都带 `fetch_mode` 字段；收货员**按整包自己的模式**做本地复核（摘要模式不要求原文），config 与整包不一致时只在 `runs.jsonl` 记一条 `fetch_mode_note`，不拒收。

### 全文模式的两条硬限制（v1.4.3）

- **篇数上限**：全文模式每次最多读 `max_candidates` 篇入围论文（默认 4；本地 `config.json → fulltext.max_candidates`，触发指令会写成 `--fulltext-max N`）。超出的候选不标记为已见，下次再参与排序。原因：feedback5 · G8 里 8 篇全文 + 23 篇相关文献跑了 48 分钟，最后因工具连续失败被平台停机。
- **命令纪律**：找引文只用 prepare 打印的 `FIND_QUOTES` 短命令 `python3 /workspace/fq <ID>`（即本技能自带的 `scripts/vendor/find_quotes.py`），禁止 `&&` 串多个 grep，一次一个文件；连续失败 2 次就停止找引文、交付结果块。详见 insp-card SKILL.md「命令纪律」。

## 2. 职责划分

| 环节 | 负责方 | 理由 |
|---|---|---|
| 触发 | 用户 | 没有无人值守运行，就不会出现 ask 死锁 |
| L0 拉取、增量、L1 去重与硬门槛、（全文模式）抓原文 | 沙箱里的 `insp_run.py prepare`（兜底时由本地 `run_local.py` 负责） | 纯脚本，结果可复现 |
| L2 生成卡片 | 平台 agent（insp-card） | 只有这一步需要判断 |
| 第一次校验 | 沙箱里的 `insp_run.py finalize` | 合并 `cards.json`（论文卡，v1.4.6 写法）与 `cards/` 单卡文件（观察型卡）；超配额自动进 rejected（不算错）；有错只改点名的那张卡，最多改 2 次，第 3 次自动只交通过的卡 |
| 第二次校验 + 入库 | 本地收货员 `receiver.py` | 不信自述，只信本地重算；状态的权威副本在本地 |
| 技能是否加载 | 收货员查 `GET /api/agent-run/{id}/skills` 和事件流 | 平台字段才是证据 |
| 状态回写 | 收货员（本地 `state.json` → 会话沙箱 `/workspace/inspiration_state/` + 记忆 `[灵感状态]`） | 下次在同一会话或新会话都能去重 |

**权威状态只有一份：本地 `inspiration/state.json`。** 沙箱里的状态和记忆里的摘要都只是投影；三者冲突时以本地为准，收货员入库时会按本地状态再去重一次。

## 3. 状态解析顺序（prepare 打印 MODE）

1. `attached`：`/workspace/_refs/` 下能找到 `state.json`（方式 ②③）。
2. `persisted`：`/workspace/inspiration_state/state.json` 存在（同一会话上次运行留下的，或收货员推回来的）。
3. `bootstrap`：以上都没有，从技能自带的 `assets/state_template/` 复制一份。这时 `--exclude` 传进来的 ID 视为“已见”，最后由收货员按本地状态兜底去重。

附件里已经有 `triage.json` 时（方式 ③），prepare 不再抓取，直接使用附件。

## 4. 输出约定

- 工作目录：`/workspace/inspiration_out/`
  - `triage.json`（含 `fetch_mode`；全文模式另有 `ft_<ID>.md`、`rel_<ID>.md`、`fulltext_index.json`）：由 prepare 生成，**agent 不得修改**
  - `cards.json`：agent 按 insp-card 契约写入
  - `bundle.json`：由 finalize 生成，是收货员优先读取的文件
- 结果块：`<<<INSP_BUNDLE_JSON` 和 `INSP_BUNDLE_JSON>>>` 各占一行，块内是与 `bundle.json` 完全相同的 JSON。文件读不到时，收货员从运行记录 / 事件流里取结果块（finalize 自己打印的那份优先，所以模型抄写出错也不影响）。
- v1.4.2：整包自带 `triage_min`（收货员复核需要的 triage 字段）和 `triage_min_sha256`，只拿到结果块也能完成本地复核；校验和对不上即拒收。
- 一次回答里只能有一个结果块；结果块之外的说明不超过 10 行。
- 旧版结果块 `INSP_CARDS_JSON` 仅在方式 ③ 里继续兼容。

整包的顶层字段：

| 字段 | 含义 |
|---|---|
| `bundle_version` | 固定 `insp-bundle/1.0`（收货员接受所有 `insp-bundle/` 前缀） |
| `run_id`、`generated_at`、`status`、`state_mode` | 运行标识；status ∈ OK / NO_CANDIDATES / STATE_MISSING / FETCH_BLOCKED / VALIDATION_FAILED |
| `triage_counts` | raw / seen / new / negative_filtered / gate_failed / shortlisted（由脚本生成） |
| `cards`、`rejected` | 通过沙箱内校验的卡片、被否决的候选 |
| `fetch_mode` | `abstract` 或 `fulltext`（本次运行的论文读取模式） |
| `fulltext_index` | 每篇候选的原文来源与相关文献（摘要模式为空对象） |
| `state_patch` | 新见 ID、新推送 ID、配额计数增量；收货员**按本地状态重算后**才合并 |

## 5. 成本纪律

- 不打开网页搜索；摘要模式下不得自己去抓原文；全文模式下原文由 prepare 抓取，原文文件里没有的文献不得引用。
- 不另写抓取或去重脚本；`insp_run.py` 已经包含全部步骤。
- 不生成 docx、pdf 等未要求的格式。
- 每张卡片的强模型工作量控制在几万 token 以内。

## 6. 与用户的关系

本次运行的产物只是**申请**：卡片 `status` 一律是 `proposed`，`verdict` 一律是 `null`。用户在评价页点“立刻动手”之后，才由 `run_action.py` 按分档另开任务执行。
- **收尾纪律（v1.4.5）**：输出结果块后直接结束回答，不调用 `complete` 交付工具、不放附件（详见 熔断与停止条件.md「收尾」一节）。
