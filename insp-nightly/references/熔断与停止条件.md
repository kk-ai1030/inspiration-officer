# 熔断与停止条件（v1.4）

失败时必须落在安全的一边：**最坏的结果是“这次没有新卡片”，而不是“推了重复内容，导致用户静音”。**

## 五种合法的结束状态

| 状态码 | 触发条件 | 必须输出 | 禁止 |
|---|---|---|---|
| `STATE_MISSING` | 状态文件存在但无法解析，或被截断（见下文判定） | 结果块，`status` 为 `STATE_MISSING` | 生成任何卡片；自己“修复”状态文件 |
| `FETCH_BLOCKED` | 沙箱连不上 export.arxiv.org，或退避重试后仍然 429 | prepare 已经写好的结果块（退出码 4） | 自己另写抓取代码；联网搜索替代；凭记忆列论文 |
| `NEED_INPUT` | 需要用户补充信息才能继续 | 摘要里写一行 `NEED_INPUT: <原因>`，照常交付结果块 | 调用 ask 弹表单（API 触发时无法回答，会卡死） |
| `NO_CANDIDATES` | 入围列表为空，或全部候选都没通过卡片门槛 | 一行计数摘要 + `cards` 为空的结果块 | 降低门槛来凑卡片 |
| `VALIDATION_FAILED` | finalize 第 3 次仍不通过 | finalize 自动只交通过的卡片（`AUTO_PARTIAL`，也可手动加 `--accept-partial`）；仍然一张都没有时，交出错误列表 | 删除或绕过校验项；为超配额去删文件（超配额会自动进 rejected，不是错误） |

## 收尾：不调用 complete（v1.4.5）

不管是哪种状态，交付方式都一样：结果块放在最终回答的正文里，然后直接结束。**不调用 `complete` 交付工具，不放附件。**

原因（feedback6）：有一次运行把一句说明文字“结果块已在上一行回答中原样交付”塞进了 `complete` 的 `attachments`，平台把它当成缺失的文件，要求补交；重试 3 次后以 `DELIVERY_VALIDATION_LIMIT` 强制停机。卡片其实 7 分半之前就已经入库了，用户却看到“任务已中断”，点了“从断点继续”又白跑一轮。实验证明不调 `complete` 运行能正常 completed，产物照常收货。

## 状态的判定细节

- **v1.4 允许自举**：新会话里没有任何状态时，prepare 会从技能自带的模板建一份（`MODE bootstrap`）。这时全部条目在沙箱里会被当作新增，但：
  1. `--exclude`（来自记忆 `[灵感状态]`）里的 ID 一律视为已见；
  2. 本地收货员入库时会按本地权威 `state.json` 再去重一次，已推送过的卡片不会入库，也不会通知。
  所以自举是安全的，**不属于熔断**。
- 附件或会话里有 `state.json`，但无法解析、或者 `seen_ids` 为空而 `last_run_at` 不为空（被截断）：属于熔断，输出 `STATE_MISSING`，不得退回自举。
- `negative.jsonl` 允许是空文件（还没有否决记录）。

## 本地收货员怎么处理

| 状态码 | 收货员动作 |
|---|---|
| `OK` | 本地重新校验 → 去重 → 入库 → 通知 → 打开评价页 → 把新状态推回会话沙箱和记忆 |
| `NO_CANDIDATES` | 只合并“已见 ID”和 `last_run_at`，不通知 |
| `FETCH_BLOCKED` | `receiver.auto_fallback_local=true` 时自动拉起 `run_local.py --fetch-arxiv`（本地抓取 + 自动上传），用户不用做任何事 |
| `STATE_MISSING` | 不改本地状态；在评价页状态栏显示原因 |
| 整包校验不过 / 含测试 ID（9999.*） | 拒收，写进 `inbox/receiver_status.json`，状态目录保持不变 |
